# IPTables

`iptables` is a Linux firewall utility used to control, inspect, modify, and forward network traffic.

For Red Team operations, understanding `iptables` is useful for:

- Understanding why a connection is blocked
- Allowing or restricting traffic during infrastructure setup
- Configuring SSH access
- Enabling packet forwarding
- Performing NAT and port forwarding
- Troubleshooting connectivity between compromised hosts
- Understanding how a Linux pivot or relay is configured

---

## 1. Understanding the Basic Structure

Before using `iptables`, it helps to understand three concepts:

### Chains

A **chain** is a collection of rules that traffic is evaluated against.

Common chains include:

| Chain | Purpose |
|---|---|
| `INPUT` | Traffic coming **to** the local machine |
| `OUTPUT` | Traffic generated **by** the local machine |
| `FORWARD` | Traffic passing **through** the local machine |

For example:

```bash
iptables -A INPUT ...
```

adds a rule to traffic entering the local machine.

```bash
iptables -A OUTPUT ...
```

adds a rule for traffic generated by the local machine.

```bash
iptables -A FORWARD ...
```

controls traffic being routed through the machine.

---

## 2. List Current Rules

To inspect the current firewall configuration:

```bash
iptables -L
```

A more useful version for troubleshooting is:

```bash
iptables -L -v --line-numbers
```

### What the options mean

- `-L` → list rules
- `-v` → verbose output, including packet/byte counters and interfaces
- `--line-numbers` → display rule numbers

Example:

```text
Chain INPUT (policy ACCEPT)
num  pkts bytes target  prot opt in   out source      destination
1    120  8500 ACCEPT  tcp  --  eth1 *   10.0.0.0/8  0.0.0.0/0
2    15   1200 DROP    all  --  *    *   1.2.3.4     0.0.0.0/0
```

The line numbers become especially useful when you want to delete a specific rule.

For example:

```bash
iptables -D INPUT 2
```

deletes rule number `2` from the `INPUT` chain.

---

# 3. Policies vs Rules

This is one of the most important concepts to understand.

A chain has a **default policy**.

For example:

```bash
iptables -P INPUT ACCEPT
```

means:

> If incoming traffic does not match an `INPUT` rule, allow it.

Whereas:

```bash
iptables -P INPUT DROP
```

means:

> If incoming traffic does not match an `INPUT` rule, drop it.

For example:

```bash
iptables -P INPUT DROP
```

sets the default `INPUT` policy to `DROP`.

This is different from adding a `DROP` rule.

### Why?

Rules are evaluated first.

If a packet matches an `ACCEPT` rule, it can be accepted even when the default policy is `DROP`.

Conceptually:

```text
Packet
  |
  v
INPUT chain
  |
  +--> Rule 1 matches? ---> ACCEPT
  |
  +--> Rule 2 matches? ---> DROP
  |
  +--> No rule matched
             |
             v
       Default Policy
             |
             v
            DROP
```

# 4. Flush Rules

To remove all rules from the default filter table:

```bash
iptables -F
```

`-F` means **flush**.

Important:

```bash
iptables -F
```

**does not change the chain policies.**

For example, suppose you have:

```bash
iptables -P INPUT DROP
```

and then execute:

```bash
iptables -F
```

The individual rules are removed, but the policy remains:

```text
INPUT policy: DROP
INPUT rules:  none
```

Therefore, incoming traffic can still be dropped.

This distinction is extremely important when troubleshooting a machine that suddenly becomes inaccessible.

### Resetting both rules and policies

If you intentionally want to return the main filter chains to an accept-all state:

```bash
iptables -F

iptables -P INPUT ACCEPT
iptables -P OUTPUT ACCEPT
iptables -P FORWARD ACCEPT
```

Use this carefully on remote systems because changing firewall rules can immediately affect your SSH connection.

---

# 5. Setting INPUT Policy to DROP

A common firewall configuration starts with:

```bash
iptables -P INPUT DROP
```

This follows a **default deny** approach:

> Allow only the traffic that has been explicitly permitted.

For example, if SSH is supposed to be available, an explicit SSH rule must be added.

The important idea is:

```text
Default = DROP

Allowed traffic
      |
      +--> explicit ACCEPT rule
```

This is generally safer than:

```text
Default = ACCEPT

Blocked traffic
      |
      +--> explicit DROP rule
```

because the second approach can accidentally leave unexpected services exposed.

---

# 6. Allowing Established and Related Connections

A very common rule is:

```bash
iptables -A INPUT -i eth1 -m state --state RELATED,ESTABLISHED -j ACCEPT
```

This allows packets belonging to connections that are already established or related to an existing connection.

### Breaking it down

```text
-A INPUT
```

Add the rule to the `INPUT` chain.

```text
-i eth1
```

Only apply it to traffic entering through `eth1`.

```text
-m state
```

Use the connection-state matching module.

```text
--state RELATED,ESTABLISHED
```

Match connections that are:

- `ESTABLISHED` → already part of an existing connection
- `RELATED` → related to an existing connection

```text
-j ACCEPT
```

Accept matching packets.

This rule is extremely common in stateful firewall configurations.

---

# 7. SSH Example

Suppose the machine needs to establish outbound SSH connections through `eth1`.

You could allow new and established SSH traffic with:

```bash
iptables -A OUTPUT -o eth1 -p tcp --dport 22 \
-m state --state NEW,ESTABLISHED -j ACCEPT
```

This applies to outbound TCP traffic:

```text
OUTPUT
  |
  +--> eth1
       |
       +--> TCP
            |
            +--> destination port 22
```

The `NEW` state allows a new SSH connection to be initiated.

The `ESTABLISHED` state allows packets belonging to an existing SSH connection.

---

## 8. Allowing the Return Traffic

The response traffic needs to be allowed as well.

For example:

```bash
iptables -A INPUT -i eth1 -p tcp --sport 22 \
-m state --state ESTABLISHED -j ACCEPT
```

Here:

```text
--sport 22
```

means the source port is `22`.

This makes sense for the response direction:

```text
Client
  |
  | destination port 22
  v
SSH Server
  |
  | source port 22
  v
Client
```

A useful mental model is:

```text
OUTPUT:
local machine ---> TCP/22 ---> SSH server

INPUT:
SSH server ---> source TCP/22 ---> local machine
```

In modern Linux systems, `-m conntrack --ctstate` is also commonly used instead of the older `-m state --state` syntax.

For example:

```bash
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```

# 9. Packet Forwarding

Normally, a Linux machine primarily handles traffic destined for itself.

But a Linux host can also act as a router.

To enable IPv4 packet forwarding:

```bash
echo "1" > /proc/sys/net/ipv4/ip_forward
```

This changes:

```text
ip_forward = 0
```

to:

```text
ip_forward = 1
```

Conceptually:

```text
Host A
   |
   v
Linux Router
   |
   v
Host B
```

Without forwarding enabled:

```text
Host A ---> Linux ---> X
```

The Linux machine receives the packet but does not route it onward.

With forwarding enabled:

```text
Host A ---> Linux ---> Host B
```

the Linux machine can route the packet between interfaces.

### Check the current value

```bash
cat /proc/sys/net/ipv4/ip_forward
```

A result of:

```text
1
```

means forwarding is enabled.

A result of:

```text
0
```

means forwarding is disabled.

# 10. DNAT and Port Forwarding

`iptables` can also modify packet destinations using **DNAT** (Destination Network Address Translation).

For example:

```bash
iptables -t nat -A PREROUTING \
-i eth1 \
-p tcp \
--dport 3389 \
-j DNAT \
--to 192.168.1.2:3389
```

This is a port-forwarding rule.

It says:

> TCP traffic arriving on `eth1` with destination port `3389` should have its destination changed to `192.168.1.2:3389`.

Conceptually:

```text
External Host
      |
      | TCP/3389
      v
Linux Router
      |
      | DNAT
      v
192.168.1.2:3389
```

This is commonly used when a Linux machine sits between two networks.

---

## 11. Understanding PREROUTING

The rule above uses:

```bash
-t nat
```

to select the `nat` table.

And:

```bash
-A PREROUTING
```

to add the rule to the `PREROUTING` chain.

`PREROUTING` is processed before the routing decision is made.

A simplified packet flow is:

```text
Incoming packet
      |
      v
PREROUTING
      |
      | DNAT can happen here
      v
Routing decision
      |
      +------> INPUT
      |
      +------> FORWARD
```

This is why DNAT is commonly performed in `PREROUTING`.

---

# 12. Viewing NAT Rules

To list NAT rules:

```bash
iptables -t nat -L
```

For a more useful view:

```bash
iptables -t nat -L -v --line-numbers
```

The important difference is:

```bash
iptables -L
```

lists the default `filter` table.

While:

```bash
iptables -t nat -L
```

lists the `nat` table.

---

# 13. The Main iptables Tables

You will commonly encounter these tables:

| Table | Main purpose |
|---|---|
| `filter` | Allowing/blocking traffic |
| `nat` | Network Address Translation |
| `mangle` | Packet modification |
| `raw` | Special packet handling / connection tracking control |

When you run:

```bash
iptables -L
```

you are normally working with the `filter` table.

When you run:

```bash
iptables -t nat -L
```

you are explicitly selecting the `nat` table.

# 14. Red Team Perspective

During an engagement, you may encounter a compromised Linux host with multiple interfaces:

```text
eth0 -> Internet / external network
eth1 -> Internal network
```

The host might be able to communicate with both networks:

```text
                Linux Host
             +-------------+
Internet ----| eth0     eth1|---- Internal Network
             +-------------+
```

If IP forwarding is enabled:

```bash
echo "1" > /proc/sys/net/ipv4/ip_forward
```

the machine can potentially act as a router.

`iptables` can then control how traffic moves between the interfaces.

For example:

```text
External
   |
   | TCP/3389
   v
eth0
   |
   | DNAT
   v
192.168.1.2:3389
```

This is why understanding `iptables` is useful when working with:

- Pivoting
- Port forwarding
- Internal network access
- Multi-homed hosts
- Traffic redirection
- NAT
- Linux-based relay hosts

---

# 15. Important Operational Warning

Be extremely careful when modifying `iptables` over SSH.

For example:

```bash
iptables -P INPUT DROP
```

can immediately make the machine inaccessible if you have not already allowed your SSH connection.

A safer workflow is:

```text
1. Inspect current rules
        |
        v
2. Add required ACCEPT rules
        |
        v
3. Verify the rules
        |
        v
4. Change the default policy
        |
        v
5. Test connectivity
```

Keep an existing SSH session open while testing firewall changes.

If the new rules lock you out, the existing session may remain available long enough to fix the configuration.

# Quick Reference

### List filter rules

```bash
iptables -L -v --line-numbers
```

### Set default INPUT policy

```bash
iptables -P INPUT DROP
```

### Flush rules

```bash
iptables -F
```

> `iptables -F` removes rules but does **not** change chain policies.

### Allow established/related inbound traffic

```bash
iptables -A INPUT -i eth1 \
-m state --state RELATED,ESTABLISHED -j ACCEPT
```

### Allow outbound SSH

```bash
iptables -A OUTPUT -o eth1 -p tcp --dport 22 \
-m state --state NEW,ESTABLISHED -j ACCEPT
```

### Allow established SSH responses

```bash
iptables -A INPUT -i eth1 -p tcp --sport 22 \
-m state --state ESTABLISHED -j ACCEPT
```

### Enable IPv4 forwarding

```bash
echo "1" > /proc/sys/net/ipv4/ip_forward
```

### DNAT TCP/3389

```bash
iptables -t nat -A PREROUTING \
-i eth1 -p tcp --dport 3389 \
-j DNAT --to 192.168.1.2:3389
```

### List NAT rules

```bash
iptables -t nat -L
```

### List NAT rules with counters and line numbers

```bash
iptables -t nat -L -v --line-numbers
```

The most important thing to remember is:

```text
                    Incoming
                       |
                       v
                  PREROUTING
                       |
                 Routing decision
                   /         \
                  /           \
                 v             v
              INPUT        FORWARD
                 |             |
                 v             v
              Local          Another
              Host            Host

Outgoing local traffic
         |
         v
       OUTPUT
         |
         v
    POSTROUTING
```

If you understand **chains + policies + tables + packet direction**, most `iptables` commands become much easier to read.
